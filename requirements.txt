requests>=2.31
pyyaml>=6.0.2
openpyxl>=3.1
xlrd>=2.0

# openpyxl is required, not optional: of the 191 spreadsheets in the 63-paper
# development corpus, 172 are .xlsx, and they are where sample-level metadata
# actually lives. That corpus is not in this repository -- see the note in the
# README about where these counts come from.
#
# xlrd is required for the same reason, on a measurement that moved. It was an
# optional extra for as long as the development corpus held one .xls among those
# 191 spreadsheets: not worth a dependency. Over the live 393-article corpus it is
# 56 files and 129 MB, every one of them reported `unsupported_format` on an
# install without it, and that is the largest block of supplementary material this
# stage does not read. A dependency that decides whether 129 MB of tables are
# extracted is not an extra. Installing it is necessary but not sufficient:
# `extract.extractor._parser_versions` has to name it too, or the extraction cache
# keeps serving the verdict from before it was there.
#
# The xlrd floor is not what makes .xls readable -- 1.2.0 read this format too --
# it is which library owns .xlsx. 2.0 is the release that dropped .xlsx support,
# and with the floor there the two spreadsheet parsers cannot both claim a file:
# `spreadsheet` dispatches .xlsx to openpyxl and .xls to xlrd, and an xlrd 1.x
# install would answer for both.
#
# The pymupdf floor starts from the version the checked-in section-score baseline
# was measured on. `tests/expected_section_scores.json` does not reproduce on any
# release before 1.28.0 -- see the note beside it -- and 1.24.0 has no cp313 wheel
# at all, so the old `>=1.24` was also unsatisfiable on one leg of the CI matrix.
# 1.28.0 ships a cp310-abi3 wheel, so it covers 3.10 through 3.13 from one build,
# and its own `requires_python` is `>=3.10`, matching this project's.
#
# The patch digit is load-bearing for a second reason, and it is not about how a
# page reads. `extractor._parser_versions` records pymupdf at full precision, so
# the patch is in `extraction_key`, and a floor of `>=1.28` admits two installs
# that disagree about it. On 2026-08-27 that split one corpus in two: 212 articles
# keyed to 1.28.0 and 181 to 1.28.2, written by two interpreters on the same
# machine, neither of them wrong about the floor, and nothing in the corpus saying
# a mixture was what came out. The labeller scores the same under both -- 98/87 and
# 125/115 on the two pinned papers, measured on each -- so flooring at 1.28.2 costs
# no baseline and removes one of the two answers.
#
# It narrows the hole rather than closing it. A floor binds `pip install`, not a
# `python -m manuscript_harvest.extract.cli` run under whichever interpreter is on
# PATH: that is how the 1.28.0 half arrived, from a cwd that put this package on
# `sys.path` and an environment that had never installed it.
#
# The pyyaml floor is set by wheel availability across the whole supported range,
# not by an API this code needs: cp312 wheels start at 6.0.1 and cp313 wheels at
# 6.0.2, so `pyyaml==6.0` cannot be installed on two of the four interpreters
# `requires-python = ">=3.10"` promises.
#
# The requests and openpyxl floors are NOT load-bearing, and are written down here
# because every other line in this file is read as "this floor exists for a
# reason". The suite passes at requests 2.25.1 and openpyxl 3.0.10, and
# `reset_dimensions` -- the openpyxl call that looks like it would need 3.1 -- is
# present in 3.0.10 and guarded by an except anyway. Keep requests at 2.31
# regardless: that is the release which stopped Proxy-Authorization leaking across
# a cross-host redirect (CVE-2023-32681), and this tool authenticates through an
# institutional proxy, so it is the one dependency where that class of bug would
# reach real credentials.
#
# One optional extra:
#   requirements-browser.txt   the institutional-proxy tier (Playwright)
#
# Word documents, zips and JATS XML need nothing beyond the standard library.
